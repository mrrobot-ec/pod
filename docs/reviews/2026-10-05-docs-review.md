# Docs review: v1 documentation set against the design spec

Date: 2026-10-05. Source of truth: `docs/specs/2026-10-05-pod-design.md`. Every file listed in the brief was read in full against the spec. Fixes were made in place with targeted edits. Format of each bullet: file; what was wrong; what changed; severity.

## Summary

- 26 mismatches fixed (25 in the docs, 1 formatting fix in the spec edit).
- ASSUMPTION markers: 58 occurrences before and after. 3 of them are cross-references to the convention (the header lines of `commands-workers.md`, `commands-messages.md`, `state-machines.md`), so there were 55 notes. 4 were resolved and deleted because the spec answers them. 5 were narrowed: the spec answered the main point, so it is now stated as fact and only the leftover detail is still marked. 1 was a risky inference; it was fixed and its note kept. 4 new notes were added where the review exposed inferences that had not been marked. 55 notes remain.
- 4 places where the spec contradicts itself, plus 1 ambiguity, are listed at the end.
- Acceptance checks: README links resolve; every code in `errors.md` appears on a commands page; the unfinished-marker grep from the brief returns nothing; every file is under 400 lines (the spec is 739 lines and was not resized); no em-dashes outside the spec.

## Findings

### High

- `docs/examples/full-run.md`: released the implementer (step 6) before the review. That contradicts spec section 1, success criterion 2: in the terra to sol loop, findings go back to the first worker in the same pane. It also contradicted the example's own step 8 text ("reuse its pane ... before releasing"). Changed: step 6 now keeps the implementer `reclaimable` until the review is in; step 7's `worker-list` shows both workers; step 8 explains the fix path as a new Task plus `worker-start --terminal terra-k3x9`; step 9 releases both. Severity: high.
- `docs/guides/coordinator.md`: "If it is wrong, start a retry with `--retry-of`" after a `worker_done --outcome succeeded`. The Task is then `completed`, and spec section 7.5 allows `--retry-of` only for `failed` or `blocked` Tasks, so the guide told agents to run a command that is always refused. Changed: the guide now says to create a follow-up Task and reuse the pane, or start a fresh worker. Severity: high.
- `docs/reference/errors.md`, `docs/reference/commands-messages.md`, `docs/reference/commands.md`: showed `settled` as an error envelope on stderr that exits 0. That contradicts the error contract in spec section 6: errors go on stderr and exit 1. Changed: `settled` with `duplicate: true` is now a normal receipt. It moved to "Values that look like errors but are not", was removed from the `send` error list, and the example now has a receipt shape. The exit-0 ASSUMPTION is kept. Severity: high.
- `docs/reference/state-machines.md` T12: `gate-create` was allowed only from `dispatched`. Spec section 9 refuses a gate only while a supervised worker is live on the Task; otherwise it "completes the Task's active Dispatch" (if any) and blocks the Task. Gates are for coordinator-owned DAG decisions, which are usually made on `pending` or `ready` Tasks. Changed: From is now `pending`, `ready`, `dispatched`, and the diagram was updated. Severity: high.

### Medium

- `docs/reference/state-machines.md` T14 to T16: T14 let `task-update` set any status, including `dispatched`, and applied the live-worker guard to every status. Spec section 9 guards differ by target status. Changed: split into T14 (pending, ready, blocked), T15 (dispatched, requires an active Dispatch), T16 (refusals while a Dispatch is active), T17 (completed or failed with no live worker, firing T3), and T18 (completed or failed refused while a worker is live, for example after `worker_done` and before release). The T14 ASSUMPTION was removed because the spec answers it. Severity: medium.
- `docs/reference/state-machines.md` T10, T11: both were missing from-states. The breaker can trip on a start or `dispatch --inject` failure while the Task is still `ready` (spec section 7.5). A `start_unknown` on a `--retry-of` start blocks a `failed` or `blocked` Task (spec section 7.1). Changed: added the from-states and rewrote the note on failed starts, which wrongly attributed them to T9. Severity: medium.
- `docs/reference/state-machines.md` worker diagram: the arrows showed W7 and W11 leading from `ready` to `failed`/`start_unknown`. Changed: redrew the diagram so it matches the W-table. Severity: medium.
- `docs/reference/commands-workers.md` and `state-machines.md` R5: `worker-abandon` left the worker `retained`. That was a risky inference. It skips the spec section 7.4 accounting choice and hides the worker from the reclaimable check, and a retained worker needs a recorded reason, which abandon does not supply. Changed: abandon now leaves the worker `reclaimable`. Release still leaves active or unproven panes alone, so nothing unsafe is closed. The receipt and diagram were updated and the note kept. Severity: medium.
- `docs/reference/errors.md`, `commands-workers.md`, `commands.md`: `dispatched_unobserved` was listed as an error code with an error envelope. Spec sections 7.1 and 13 call it an outcome, and `commands-workers.md` already showed it as a receipt field. Changed: it moved to "Values that look like errors but are not", was removed from the `worker-start` and `dispatch` error lists, and the commands index now has a "reported in a receipt" table. The exit-1 ASSUMPTION is kept. Severity: medium.
- `docs/ops/troubleshooting.md` "Agent exits without reporting": told the reader to retry with `--retry-of` after stop or abandon. A Task below the breaker goes back to `ready`, where `--retry-of` is refused (spec section 7.5). Changed: start with `--task` when the Task is `ready`, and add `--retry-of` only when it is `failed` or `blocked`. Severity: medium.
- `docs/examples/full-run.md` step 8: the reviewer ran long enough to heartbeat, but its Delivery held only `worker_done`. Spec section 8.3 says the Delivery is always the whole batch, and heartbeats go to `run:<id>` (spec section 8.1). Changed: added a heartbeat row and a sentence explaining it. Also made the `--types` lists match the guide (`decision_gate` added). Severity: medium.
- `docs/guides/coordinator.md`: was missing the placement rule from spec section 7.2 ("a fresh worker means a fresh agent pane, not a new worktree; create a worktree only when asked or on a concrete filesystem conflict"). The guide is served verbatim to coordinators, so this rule belongs there. Changed: added it to step 3. Severity: medium.
- `docs/guides/coordinator.md` "Other endings": juxtaposed "`worker_done --outcome failed` fails the Task directly" with "below 3 a failed Dispatch returns the Task to ready" with no distinction, which read as a contradiction. Changed: "any other failed Dispatch" now leaves or returns the Task `ready`, and a `ready` Task is started again with `--task`, not `--retry-of`. Severity: medium.
- `docs/reference/commands-workers.md` `worker-stop`: the receipt showed Dispatch `failed` without marking that as an inference. The spec says only "fences". Changed: the ASSUMPTION now covers the Dispatch status and its effect on the breaker, linked to D8. Severity: medium.

## Spec-internal inconsistencies (docs follow the more specific section)

- Section 7.5: "`worker_done --outcome failed` fails the Task directly" sits beside "a failed Dispatch below 3 returns the Task to `ready`", and the spec does not say whether a reported failure increments `failure_count`. The docs treat the reported failure as the specific rule (Task `failed`) and mark the counting as an ASSUMPTION (`state-machines.md` notes).
- Section 9: `gate-resolve` "sets the Task `ready`" even for a gate created on a `pending` Task whose dependencies have not completed, which conflicts with the dependency rule in the same section. The docs follow the gate rule literally and point out the conflict (`state-machines.md` T13 note).
- Section 7.4 says release archives the final screen text. Section 11 says it is archived at release "for kinds without a reader". The docs follow section 7.4, the release procedure, and archive in every case.
- Section 1 says the reviewer runs "at high effort", while the glossary and the section 4 `sol` preset say `xhigh`. The docs use `xhigh` from the config section.
- Ambiguity (not a contradiction): sections 8.1 and 6. `settled` is "returned" for a duplicate `worker_done`, but section 6 sends every error to stderr with exit 1. The docs treat `settled` as a success receipt.
