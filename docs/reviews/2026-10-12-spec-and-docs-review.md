# Spec and docs review

Date: 2026-10-12. Source of truth: `docs/specs/2026-10-05-pod-design.md`, reviewed and corrected in place. All 16 input files were read in full, including the previous review, which is unchanged. This is a document-contract review, not an implementation or live herdr/dagr test.

## Verdict per addition

1. **Closure reasons: fixed.** Keep the idea. Section 8.1 permits all seven reasons with either outcome, but the preamble omitted `no_follow_on` for failures and section 14 implied every report needed a target. Those now agree. Stop/abandon record `canceled` only when fencing an active Dispatch and preserve accepted endings; fencing is still not worker-reported settlement under 7.4. Failed starts and gate completion have no worker-reported reason. Requiring reasons on failed reports is an intentional section 14 incompatibility: existing Orca failed-report commands need updating, while ordinary successful reports keep their default. No new failure-count rule was introduced.
2. **Safe pane input: fixed.** Keep paste, confirm, then submit. Section 19's type-plus-Enter fallback directly violated section 8.2 and mislabeled submitted input as Enter-withheld. The fallback now withholds input, preserves stored mail, and reports failed or uncertain initial injection with recovery instructions. Multi-line preambles retain embedded newlines without submission. A later attempt cannot append to or submit uncertain leftover text; it skips until input is proven cleared. This changes adapter behavior, not the successful command contract. The fallback deliberately loses automatic injection when the safety prerequisite is unavailable.
3. **Wake ladder: fixed, with a v1 concern.** Keep durable attention tracking. A mandatory idle event at rung 2 could strand an already-idle recipient, and “any command” made read-only inspection type into panes. Later idle hooks or mutating commands can now advance the next rung, once per invocation; rungs 4 and 5 retain the 60-second minimum. Only nudge records count, including skipped attempts; preamble records do not. New mail does not reset a pending ladder. Read-only commands do not type, and without a later trigger nothing advances: exhaustion is not an elapsed-time guarantee. This is implementable with section 3.2's bounded processes and hooks, but the exact five-rung design is more machinery than v1 needs. The section 14 difference remains explicit.
4. **Three-axis taxonomy: fixed.** Keep independent activity, process presence, and input need. The old table overlapped “present + unknown activity” with blocked input, omitted other combinations, and provided no representation for unproven presence. Presence may now be null; present always derives `live`, with input attention independently added, while confirmed exit/absence derives `exited`. Unknown activity is not unknown presence, and old screen text or a heartbeat alone cannot prove current process presence. Exit failure attention applies only to unsettled attempts, and recorded success/failure/stop/abandonment takes precedence over `outcome_unknown`, including on the board. This preserves the three Orca liveness verdicts and the rule against acting destructively on `unverifiable`; the additional axes remain the section 14 extension.
5. **Escalation routing: fixed.** Keep specialist questions, evidence, and user decisions. Explicit `ask --to` does not change the default Run mailbox; its two copies now identify one question, either ID may be replied to, and the asking Dispatch owns it. The coordinator can answer if the specialist disappears. Eligible specialists need an active Dispatch and live presence in the same Run, excluding the asker. Question waits do not occupy the single `check --wait` slot. Coordinator gates require a Task; untasked user gates have null `task_id`, mutate no Task/Dispatch, and export a board-only card using the gate ID. User-gate resolution sends an engine-generated notification exempt from worker lifecycle identity. Missing options and invalid recommendations have the named validation error, and the preamble now includes `reply`. Required evidence on escalations is another intentional section 14 incompatibility for old Orca commands; specialist routing and user gates are opt-in extensions.

The spec has **27 localized edit hunks**, counted with a three-line-context unified comparison against the pre-review copy, including formatting. In addition to the corrections above, its failure summary now conditions reclaimability on creation of a pane, the testing list covers the corrected cases, the glossary matches the corrected rules, the attribution includes escalation routing, and the review status and em-dash formatting were updated. No wholesale rewrite or new feature was added.

## Over-specification to consider cutting, not cut

- Seven closure-reason categories plus mandatory same-Run target validation could begin as a reason string and optional reference. The essential idea is an explicit explanation for an unsuccessful attempt, not a seven-value taxonomy.
- Exactly five wake attempts, distinct rung names, 15-second observation freshness, three-second quiet time, and the late-rung 60-second interval could be one bounded retry policy. Preserve durable mail, safe input, and visible exhaustion.
- Recording every preamble and nudge input attempt in `wake_attempts` mixes injection diagnostics with mailbox attention. V1 could keep only nudge state and a minimal last-input receipt.
- Ranked evidence and screen sampling add reconciliation rules beyond the three-axis idea. V1 could use authoritative process observations plus null/unknown values, retaining independent input attention.
- Pre-rendered specialist rosters and copied questions with first-reply arbitration add stale-roster and alias handling. V1 could route all questions through the coordinator without losing the rule that blockers go to their knowledge owner.
- User-gate decision cards, sidebar `DECISION`, mandatory structured evidence/options/defaults, and untasked synthetic board rows could start as a single durable user question with an evidence reference. Keep one human decision and a recorded answer.

These remain in the spec; choosing a smaller v1 is the owner's decision.
