# Error codes

Errors are written to stderr as `{"error": {"code", "message", "data": {"nextSteps"}}}`. Exit 1 means a refused or failed operation; exit 2 means a usage error. Every code below exits 1 unless the table says otherwise. Which commands return each code is listed in the [command reference](commands.md#error-code-index).

The `data.nextSteps` column says what pod tells the caller to do. The spec names the codes and their meaning, not their message text, so the exact wording pod prints can differ slightly from this summary. The code and exit are as shown.

| Code | Raised when | `data.nextSteps` | Exit |
|---|---|---|---|
| `task_not_found` | `worker-start` preflight, or any command naming a Task (or dependency, or parent) that does not exist in the Run. | Run `pod task-list` to see the Run's Tasks, then retry with a valid ID. | 1 |
| `task_not_startable` | `worker-start` on a Task that is not `ready`, or is `failed` or `blocked` without a valid `--retry-of`. `data` also carries `status` and `unmetDependencies`. | Finish or retry the unmet dependencies listed in `data.unmetDependencies`, or pass `--retry-of <dispatch_id>` for a `failed` or `blocked` Task. | 1 |
| `nested_worker_depth_exceeded` | `worker-start` would exceed `defaults.nested_depth_max` (default 1: workers may not start workers). | Ask your coordinator to start the worker instead, or raise `nested_depth_max` in `config.toml`. | 1 |
| `worker_identity_changed` | A lifecycle message (`worker_done`, `heartbeat`, `escalation`, `decision_gate`) comes from a terminal whose ID matches the Dispatch but whose recorded agent process is not an ancestor of the calling `pod` process. | Do not retry. The message was stored as a `status` message for the coordinator; stop work and go idle. | 1 |
| `caller_fenced` | A lifecycle message comes from a terminal whose ID does not equal the Dispatch's, or whose Dispatch was fenced (stopped or abandoned). | Do not retry. The message was stored for the coordinator; stop work and go idle. | 1 |
| `not_in_herdr` | A mutating command that needs a caller identity runs with `HERDR_ENV` unset. | Run the command from a pane inside herdr. Read-only commands work outside herdr with `--run <id>`. | 1 |
| `remote_unsupported` | `worker-start --on` is used. Remote placement is not in version 1. | Remove `--on` and start the worker locally. | 1 |
| `consumer_fenced` | A worker's `check --terminal <handle>` is called after its Dispatch is no longer the worker's. | Stop work. Do not send `worker_done`. Go idle and wait for a new brief. | 1 |
| `waiter_exists` | A second `check --wait` is started on a Run that already has a waiter. | Only one `check --wait` per Run; `ask` waits independently. Wait for the other `pod check --wait` to return, or find and end it, then retry. | 1 |
| `store_access_denied` | The store directory is not writable, typically inside an agent sandbox. | Print the exact fix for the detected agent kind: for Claude, allow writes to the pod state directory in the sandbox settings; for Codex, add the state directory to the sandbox's writable roots. See [troubleshooting](../ops/troubleshooting.md#store_access_denied). pod picks the text at runtime from the caller's environment; any other caller is told to make the state directory writable. | 1 |
| `source_changed` | `worker-read` is given a `--cursor` pinned to a source (transcript or terminal) that is not the source now being read. | Restart reading without `--cursor`, or force the original source with `--source`. | 1 |
| `inactive_dispatch` | A `worker_done` conflicts with an outcome already recorded for the Dispatch, or arrives for a Dispatch that is no longer active. | Do not retry or send another lifecycle message from the inactive Dispatch. The rejected report is stored for the coordinator; go idle. | 1 |
| `closure_reason_required` | `send --type worker_done --outcome failed` without `--reason`. A successful `worker_done` defaults to `no_follow_on` and never raises this. | Resend with `--reason <no_follow_on \| handed_off \| blocked_on \| denied \| canceled \| escalated \| superseded>`; for `handed_off`, `blocked_on`, or `superseded` add `--reason-target <task or dispatch id>`. | 1 |
| `closure_target_required` | `worker_done` with `--reason handed_off`, `blocked_on`, or `superseded` and no `--reason-target`. A target that is given but that pod cannot find in the Run is not refused; the report is accepted with a `warnings` entry. | Resend with `--reason-target <task or dispatch id>` naming where the work went or what it waits on. | 1 |
| `question_answered` | `reply` to a question that is already `answered`. With a routed question (`ask --to`), the first `reply` wins and every later one gets this code. | Do nothing. The asker can retrieve the answer with `pod ask --resume <original_message_id>`; do not assume an unread mailbox contains it. | 1 |
| `recipient_not_live` | `ask --to dispatch:<id>` names a Dispatch that is not a live worker in the sender's Run, or names the asker's own Dispatch. | Pick a worker listed under `=== SPECIALISTS ===` in your preamble, or ask the coordinator by leaving out `--to`. | 1 |
| `escalation_evidence_required` | `send --type escalation` without `--evidence` or without `--recommendation`. | Resend with `--evidence <file path, message ID, or worker-read cursor>` and `--recommendation "<what you would do by default>"`. | 1 |
| `gate_evidence_required` | `gate-create --for user` without `--evidence`, `--recommendation`, or a nonempty `--options` list, or with a recommendation that is not one of the `--options`. | Resend with an evidence reference and a recommendation taken from the options. | 1 |
| `herdr_unreachable` | The herdr server socket cannot be reached (no server for this session, or the socket path is wrong). | Start herdr or attach to the session, check `herdr status server`, then retry. | 1 |
| `herdr_error` | herdr answered a request with an error. `message` carries herdr's error text. | Run `herdr status server` and retry; if it persists, report the herdr error text. | 1 |
| `terminal_busy` | A `worker-start --terminal` or `dispatch --to` target terminal already owns an active Dispatch. | Wait for that worker's `worker_done`, or stop it with `pod worker-stop --dispatch <id>`, then retry. | 1 |
| `unknown_agent` | An `--agent` name resolves to no preset, command alias, or herdr agent kind, including an unconfigured name that is on `PATH` (spec section 4). | Use a preset or alias from `config.toml`, or a herdr agent kind such as `codex` or `claude`. | 1 |
| `launch_mapping_unsupported` | `--model`, `--effort`, or `--yolo` (from the command line or a preset) for an agent kind whose launch table leaves that flag empty, or `--fast` for a kind without a `fast` entry (`claude`, and every kind with no table; spec section 4). | Remove the flag (`nextSteps` names the preset when the value came from one), or add the snippet `nextSteps` shows, such as `launch = { model = ["--model", "{model}"] }`, under `[agents.<kind>]` in `config.toml` with the agent's own flag, or pass the agent's own flags through the preset's `args`. | 1 |
| `caller_mismatch` | A `--from` that does not match the resolved caller (spec section 3.4). | Leave out `--from`, or pass your own handle. | 1 |
| `invalid_recipient` | `send` to a group that resolves to zero recipients, a lifecycle type sent to a group, a `task:` recipient, or a sender bound to no Run that addresses anything but `run:<id>` or `dispatch:<id>`. | Address `run:<id>`, `dispatch:<id>`, a worker handle, or a group with live workers. | 1 |
| `question_closed` | `reply` to a question that is `closed` (its Dispatch failed or was fenced). A question that is already `answered` is `question_answered`. | Do nothing; the asker is gone. Send a normal message if the answer still matters. | 1 |
| `task_guard_refused` | A `task-update` or `gate-create` guard refusal: `dispatched` without an active Dispatch, another status while a Dispatch is active, `completed` or `failed` while a supervised worker is live, or a gate on a Task whose supervised worker is live. `data.guard` names the unmet guard. | Inspect the Task and its worker first; a live worker is not permission to stop it. Retry once the guard holds. | 1 |
| `reset_requires_force` | `reset` without `--force` while the Run has live workers, or `--scope all` without `--force`. `data.liveWorkers` lists the live workers. | Stop or release the live workers listed, or rerun with `--force`. | 1 |
| `limit_reached` | `worker-start` or `dispatch` while a `[limits]` cap is hit (`max_active_workers`, or `max_active_per_kind` for the worker's kind), or a fresh usage window is at `pause_above_percent`. `data` carries `limit` (`max_active_workers`, `max_active_per_kind:<kind>`, or `pause_above_percent`) with `current` and `max`, or with `window`, `usedPercent`, and `max`. | The first step names the limit and the count or window. Wait for a worker to finish or the window to reset, stop a worker with `pod worker-stop --dispatch <id>`, or raise the limit in `config.toml`. | 1 |
| `budget_exceeded` | `worker-start` or `dispatch` on a Run whose `--budget-usd` is spent: the cost its workers reported is at or above it. `data` carries `spentUsd` and `budgetUsd`. Cost is the agents' own report and may differ from the bill. | Finish the remaining work without a new worker, or start a new Run with a larger budget. | 1 |
| `usage` | Command-line or configuration input is invalid. This is the error-envelope form of a usage error. | Run the command with `--help` to see valid arguments. | 2 |

## Notes

- The split between `worker_identity_changed` and `caller_fenced`. Spec section 3.4 says a lifecycle message is accepted only when the caller's terminal ID equals the Dispatch's and the recorded agent process is an ancestor of the calling `pod`, "otherwise: `worker_identity_changed` or `caller_fenced`", without saying which is which. In pod, `worker_identity_changed` means the terminal ID matches but the agent process ancestry does not (the agent in that pane was replaced), and `caller_fenced` means the terminal or Dispatch is not the active one. If the ancestry walk is unavailable (spec section 19 fallback), only `caller_fenced` can occur.
- All rejected lifecycle messages, including closure and escalation validation refusals, are stored as `status` with priority `high` and `rejected_reason`, and delivered to the coordinator (spec section 8.1). They do not settle the Dispatch. Correct missing fields and resend; identity or fencing failures require stopping and idling.
- `gate_evidence_required` covers missing evidence, recommendation, or nonempty options, and a recommendation outside the options (spec section 9.1).
- `recipient_not_live` also covers an unknown Dispatch, another Run, or a settled Dispatch even if its agent pane is still live (spec section 9.1).
- The `data` object may carry extra fields beyond `nextSteps`. `task_not_startable` is the one the spec names: `status` and `unmetDependencies`.

## Values that look like errors but are not

- `settled`, with `duplicate: true`: the result of a repeated `worker_done` with the same outcome as the one already recorded (spec section 8.1). It is a normal receipt, not an error envelope; the first report stands and nothing changes. It exits 0, because the repeat is idempotent and the caller's goal is met.
- `dispatched_unobserved`: an outcome of `worker-start` and `dispatch --inject`. The prompt was typed into the pane but herdr reported it stalled, so the turn was not observed; the preamble is never sent twice (spec sections 7.1 and 13). Inspect the pane with `pod worker-read --dispatch <id> --source terminal` and do not resend. It exits 1, because spec section 7.1 exits 0 only for a `ready` worker; the Dispatch stays recorded.
- A `warnings` entry on an accepted `worker_done`: the `--reason-target` names a Task or Dispatch that pod cannot find in the Run. The report is accepted and settles the Dispatch, so verify the ID yourself. Exit 0.
- Worker states `failed` and `start_unknown` after `worker-start`: a start receipt (exit 1) with `failedStage`, `effects`, and `residualResources`, not an error envelope.
- Liveness and attention `unverifiable`: state could not be proven; it never authorizes action.
- `worker-read` fallback reasons `session_unproven` and `reader_unavailable`: the transcript could not be read, so screen output was returned. `no_terminal`: there was no screen to fall back to either, so no rows were returned. Exit 0.
- Attention `unreachable` and the wake outcome `rendered_unconfirmed`: a nudge could not be delivered or confirmed (spec section 8.2). They are states in `worker-list` and `wake_attempts`, never error envelopes. The message stays stored and unread.
- Projected attempt outcome `outcome_unknown`: the agent exited and its attempt has no recorded ending; recorded success, failure, stop, or abandonment takes precedence.
- The `rejected_reason` field on a stored `status` message: why a lifecycle message was refused; it holds the error code that caused it.

## Errors the spec describes without a code

The spec requires these refusals without naming a code. pod gives each a code in the table above, so that `ErrorCode` and this table stay equal (`docs_mention_no_removed_flag_or_code` enforces it): the target terminal already owning an active Dispatch is `terminal_busy`; an unresolvable `--agent` is `unknown_agent`; `--model` or `--effort` without a launch mapping is `launch_mapping_unsupported`; a mismatched `--from` is `caller_mismatch`; the `send` recipient refusals are `invalid_recipient`; a `reply` to a `closed` question is `question_closed`; the `task-update` and `gate-create` guards are `task_guard_refused`; `reset` without a needed `--force` is `reset_requires_force`. A missing Run or Dispatch named by `--id`, `--run`, or `--dispatch` stays a usage error (exit 2), as the command pages say.
